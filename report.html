Раздел 1

Постановка задачи

Реализовать алгоритмы поиска по массиву объектов авиарейс (Flight из ЛР1). Ключ поиска — поле airline (название авиакомпании). Поскольку ключи дублируются, каждый алгоритм должен возвращать все совпадения в виде std::vector<Flight>.

Структура Flight содержит: номер рейса, авиакомпанию, дату и время прилёта, число пассажиров. Реализованы пять способов поиска — четыре с нуля (без std::map/std::set) и эталонный std::multimap.

Реализованные алгоритмы

Алгоритм Средний случай Худший случай Структура
Линейный поискO(n)O(n)std::vector<Flight>
BSTO(log u)O(n)Бинарное дерево, узел: key + vector
RB-TreeO(log u)O(log u)Красно-чёрное дерево с fixInsert
Хэш-таблицаO(1 + α)O(n)Цепочки, полиномиальный хэш p=31
std::multimapO(log u + k)O(log u + k)STL (RB-Tree внутри)

u — число уникальных ключей, k — число найденных записей, α = n/m — коэффициент заполнения хэш-таблицы.

search_structures.h

linearSearch(data, key) function
Линейный поиск — последовательный обход вектора.
Сравнивает flight.airline == key для каждого элемента, собирает все совпадения.
O(n) avg/worst
class BinarySearchTree class
BST: узел хранит ключ и vector<Flight> для дубликатов.
insert(flight) — рекурсивная вставка по compareKeys. search(key) — возвращает values узла или пустой вектор.
O(log u) avg O(n) worst
class RedBlackTree class
RB-Tree с полной балансировкой при вставке.
Реализованы leftRotate, rightRotate, fixInsert. При совпадении ключа рейс добавляется в values без создания нового узла. Новые узлы — красные; корень всегда чёрный.
O(log u) avg/worst
class HashTable class
Хэш-таблица: полиномиальный хэш (p=31), метод цепочек.
Каждая корзина — vector<pair<string, vector<Flight>>>. Метод collisionCount() возвращает число коллизий при заполнении. Размер таблицы — простое число ≈ 2n.
O(1) avg O(n) worst

main.cpp

readCSV / averageSearchMicroseconds functions
Загрузка CSV и бенчмарк поиска.
readCSV читает файлы data/flights_N.csv. Для каждой размерности заполняются все структуры, затем выполняется 10 поисков по ключу «Aeroflot» с усреднением времени. Результаты сохраняются в output/search_results.csv.

// fixInsert — случай «дядя красный» + поворот «линия»
void fixInsert(Node* z) {
    while (z->parent && z->parent->color == Color::RED) {
        if (parent == grandparent->left) {
            Node* uncle = grandparent->right;
            if (uncle && uncle->color == Color::RED) {
                parent->color = uncle->color = Color::BLACK;
                grandparent->color = Color::RED;
                z = grandparent;
            } else {
                if (z == parent->right) { z = parent; leftRotate(z); }
                parent->color = Color::BLACK;
                grandparent->color = Color::RED;
                rightRotate(grandparent);
            }
        } /* симметрично для правого */
    }
}
// Полиномиальный хэш p = 31
std::size_t hash(const std::string& key) const {
    std::size_t hashValue = 0, power = 1;
    for (unsigned char ch : key)
        hashValue = (hashValue + (ch + 1) * power) % m;
    return hashValue;
}

Раздел 6

Выводы

Линейный поиск

Простейшая реализация, не требует предварительной индексации. При n = 1 000 000 занимает ~118 мс — в 15 раз медленнее хэш-таблицы. Применим только для малых массивов или разовых запросов.

BST

В среднем O(log u), но без балансировки может деградировать до O(n). На случайных данных с 10 авиакомпаниями работает приемлемо (~14 мс при n=1M), однако RB-Tree надёжнее.

RB-Tree

Гарантированный O(log u) благодаря fixInsert. При n = 1M — 13.7 мс. Хороший выбор, когда нужен упорядоченный обход ключей и предсказуемое время.

Хэш-таблица

Лучший результат на больших данных: 8.06 мс при n = 1M. Полиномиальный хэш + цепочки. Высокое число коллизий (≈ n−10) объясняется малым числом уникальных ключей при большом m.

std::multimap

Эталон STL: 58.3 мс при n = 1M — медленнее самописной хэш-таблицы из-за накладных расходов и отсутствия прямого доступа по хэшу. Удобен в production при необходимости упорядоченности.

Общий вывод: для поиска по ключу с дубликатами на больших объёмах данных (n ≥ 100 000) линейный поиск непригоден. Индексированные структуры (RB-Tree, хэш-таблица) ускоряют поиск в ~15–70 раз по сравнению с линейным при n = 1 000 000. Хэш-таблица показала наилучшее время; RB-Tree — лучший компромисс между скоростью и гарантированной сложностью без зависимости от распределения ключей.
