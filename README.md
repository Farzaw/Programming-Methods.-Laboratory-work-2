# Лабораторная работа: Алгоритмы поиска данных

Проект на C++17. Ключ поиска — поле `airline` (название авиакомпании).  
Все алгоритмы возвращают **все** совпадения: `std::vector<Flight>`.

## Сборка и запуск

```bash
python generate_data.py
mkdir build && cd build
cmake .. -G "MinGW Makefiles"
cmake --build .
./flight_search
```

Windows (MSVC):

```powershell
python generate_data.py
cmake -S . -B build
cmake --build build --config Release
.\build\Release\flight_search.exe
```

Результаты: консольная таблица и `output/search_results.csv`.

## Разбор для защиты (≈5 минут)

### 1. Балансировка красно-чёрного дерева (`fixInsert`)

После вставки новый узел всегда **красный**. Если родитель чёрный — инварианты соблюдены.  
Если родитель **красный**, нарушается правило «два красных подряд» — вызывается `fixInsert`.

Рассмотрим случай, когда родитель — **левый** потомок дедушки (для правого — симметрично):

| Случай | Условие | Действие |
|--------|---------|----------|
| **1. Дядя красный** | `uncle->color == RED` | Родитель и дядя → чёрные, дед → красный; поднимаемся к деду и повторяем |
| **2. Треугольник** | дядя чёрный/null, `z` — правый потомок | `leftRotate(parent)` — превращаем в «линию» |
| **3. Линия** | дядя чёрный/null, `z` — левый потомок | Родитель → чёрный, дед → красный, `rightRotate(grandparent)` |

**Зачем повороты:** перекраска alone не устраняет нарушение высоты чёрных путей. Повороты меняют топологию дерева, сохраняя порядок ключей и восстанавливая баланс за O(1) операций на уровень. В конце корень принудительно чёрный.

При **совпадении ключей** новый `Flight` добавляется в `values` узла без создания нового узла — балансировка не нужна.

### 2. Хэш-таблица

**Хэш-функция** — полиномиальный rolling hash с основанием **p = 31**:

h(key) = (sum of (key[i]+1) * p^i) mod m

где `m` — число корзин (простое, примерно 2× числа записей).

**Метод цепочек:** каждая корзина — `vector<pair<string, vector<Flight>>>`.  
При вставке вычисляется индекс; если корзина уже не пуста — **коллизия** (+1 к счётчику).  
В цепочке ищется запись с тем же ключом; если есть — рейс добавляется в `values`, иначе создаётся новая пара.

**Поиск:** O(длина цепочки) в корзине `h(key)`.

### 3. Теоретические сложности поиска

Пусть **n** — число записей, **k** — число совпадений по ключу, **α = n/m** — load factor хэш-таблицы.

| Структура | Средний случай | Худший случай |
|-----------|----------------|---------------|
| **Линейный поиск** | O(n) | O(n) |
| **BST** | O(log u), u — число уникальных ключей | O(n) — вырожденное дерево |
| **RB-Tree** | O(log u) | O(log u) — высота ≤ 2·log(n+1) |
| **Хэш-таблица** | O(1 + α) ≈ O(1) при малом α | O(n) — все ключи в одной корзине |
| **std::multimap** | O(log u + k) | O(log u + k) — красно-чёрное дерево STL |

Сбор результата из `vector<Flight>` в узле — O(k); это одинаково для BST, RB-Tree и Hash.

**Практический вывод:** при больших n линейный поиск и несбалансированный BST деградируют; RB-Tree, multimap и хэш-таблица дают логарифмическое или амортизированно константное время поиска ключа.
